**Понятия и правила сопоставления**  
CWE описывает тип ошибки, CVE — зарегистрированную уязвимость конкретного продукта.  
   
 CVSS задаёт численную оценку серьёзности при определённых условиях. OWASP Top 10  
   
 группирует риски веб-приложений. В данной работе используется редакция **2021**, как  
   
 в перечне категорий методички; она не выдаётся за последнюю редакцию.  
SQLi, XSS и инъекция команд веб-приложения сопоставлены с  
   
 [A03:2021 Injection.  
   
 Отсутствие проверки владельца — с  
   
 ](https://top10.owasp.org/2021/A03_2021-Injection/ "https://top10.owasp.org/2021/A03_2021-Injection/")[A01:2021 Broken Access Control.  
   
 Для консольного C++ указан N/A с пояснением: произвольное переполнение буфера  
   
 не становится A06 только из-за того, что методичка так подписала пример.](https://top10.owasp.org/2021/A01_2021-Broken_Access_Control/ "https://top10.owasp.org/2021/A01_2021-Broken_Access_Control/")  
Все cve_example — **аналоги**, не CVE, присвоенные учебным проектам.  
   
 Поле cve_relation фиксирует степень сходства. Особенно важно отличие переполнения  
   
 кучи sudo в CVE-2021-3156 от переполнения стека в нашем примере. Аналог Confluence  
   
 иллюстрирует категорию доступа, а не тождественный механизм IDOR.  
**Оценка CVSS**  
Поля cvss и cvss_vector рассчитаны для **учебной модели развёртывания**, а не  
   
 для измеренного риска данного localhost-стенда. Числа CVSS из сторонних CVE  
   
 не переносятся на учебные находки. Для веб-модели предполагается доступность  
   
 endpoint по сети, поэтому AV:N; фактические проверки шли только через loopback.  
Для C++ предполагается обработка недоверенного локального ввода процессом,  
   
 которому доверены ресурсы: AV:L и PR:L. В реальном примере пользователь запускает  
   
 свою программу со своими правами; без такой границы доверия модельная серьёзность  
   
 не описывает реального повышения привилегий. Для CPP-01 оценено подтверждённое  
   
 падение, без предположения о RCE. Для CPP-02 и CPP-03 C/I/A:H описывает потенциальный  
   
 ущерб в модели, а не выполненную демонстрацию.  
В XSS предполагаются посещение страницы жертвой (UI:R), затрагивание браузерного  
   
 контекста (S:C) и ограниченное воздействие C:L/I:L. Первоначальная серия ограничивалась HTTP; дополнительная серия  
   
 подтвердила исполнение сохранённых HTML-ответов в браузере. Для IDOR требуется обычная сессия PR:L, подтверждена утечка C:H.

 Оценки помогают объяснить условия риска, но не заменяют экспертную проверку допущений.](https://www.first.org/cvss/v3.1/specification-document "https://www.first.org/cvss/v3.1/specification-document")

**Экспертное заключение**  
Основная причина веб-дефектов — смешение пользовательских данных с SQL, HTML или  
   
 shell-командой. Параметризация и подходящие API устраняют соответствующий механизм  
   
 интерпретации. IDOR имеет другую причину: отсутствует серверное условие владения  
   
 объектом. Его нельзя исправить экранированием строки или скрытием ссылки в интерфейсе.  
В C++ управление длиной данных и форматами требует отдельной дисциплины.  
   
 Диагностическая сборка обнаружила выход за границы памяти, который Cppcheck  
   
 в данной конфигурации не выявил. Нужна комбинация исходного анализа, сканеров  
   
 и воспроизводимых динамических сценариев.  
Приоритет исправления в сетевой модели: сначала выполнение команд JS-03 и обход  
   
 входа PY-01, затем доступ к чужим заказам и XSS. Порядок для C++ зависит от реальных  
   
 прав процесса и источника ввода. Нельзя определять его по CVSS чужой уязвимости sudo.  
Все 30 сценариев завершились с ожидаемым результатом; выбранные исправления  
   
 подтверждены в пределах протоколов. Отдельно остаются CSRF, rate limiting, полная  
   
 защита сессий и зависимостей; XSS дополнительно подтверждена воспроизведением HTML в браузере. Исходные проекты  
   
 намеренно уязвимы; исправленные являются учебными производными.  
**Уточнения к методичке**  
1. В JavaScript отсутствовала инициализация таблицы users; она добавлена с тестовыми данными.  
2. В последовательном C++ main первая авария мешает остальным проверкам; введён отдельный harness.  
3. Восемь строк образца датасета покрывают пять классов; добавлена проверка уже имеющегося IDOR VulnMart.  
4. По [официальному CWE Top 25 2025 CWE-476 занимает 13-е место, а 14-е принадлежит CWE-121. В методичке эти позиции смешаны.](https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html "https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html")  
5. OWASP для C++ и численные CVSS из примеров не перенесены механически.  
6. Не подтверждённые примеры CVE из методички заменены проверенными публикациями; это не утверждение, что исходные номера обязательно не существуют.

**Вопросы к защите**  
- Почему у учебной ошибки нет собственного CVE? CVE не возникает автоматически при обнаружении класса CWE.  
- Почему одинаковый CWE не означает одинаковый CVSS? Отличаются доступность, права, взаимодействие и последствия.  
- Почему N/A корректнее выдуманной категории? OWASP Top 10 описывает веб-риски и имеет конкретную область применения.
